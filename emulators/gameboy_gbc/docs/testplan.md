# GreyMecha/Army Game Boy and Game Boy Color Test Plan

## Purpose

This document defines the evidence required to accept the implementation in
`docs/plan.md`. Testing is staged so failures are localized before cartridge
storage, display, and complete-game behavior are combined.

Tests must distinguish:

- RTL correctness in deterministic simulation.
- ECP5 fit and timing.
- RP2350 native-module and filesystem behavior.
- Electrical and clock-domain behavior on the physical badge.
- End-to-end DMG/CGB compatibility.

## Test artifacts and reporting

The implementation should provide these commands:

- `make test`: all deterministic RTL and host-side unit tests.
- `make sim-smoke`: boot the generated DMG and CGB smoke ROMs.
- `make synth`: ECP5 synthesis, place-and-route, timing, and utilization report.
- `make hardware-package`: bitstream, launcher, native module, and manifest.

Store generated reports under `gameboy_gbc/build/test-results/`, including:

- Test name, revision, tool versions, random seed, and pass/fail result.
- Simulation assertion log and waveform only for failed tests.
- Yosys utilization and nextpnr timing reports.
- Hardware firmware/bitstream hashes.
- Cache latency histogram, hit ratio, SPI error counters, and soak-test log.

Committed ROM fixtures must be generated by this project or have a reviewed
redistribution license. Commercial ROMs and Nintendo BIOS images are local-only
manual inputs and never test dependencies.

## Gate 1: source and build reproducibility

| ID | Test | Method | Pass condition |
| --- | --- | --- | --- |
| BLD-001 | Pinned upstream source | Verify manifest URLs, commits, hashes, and licenses | Every vendored file traces to a pinned source and license |
| BLD-002 | Clean build | Build in a clean checkout with documented tool versions | Bitstream and test binaries are produced without manual file edits |
| BLD-003 | No proprietary payloads | Scan tracked files and build inputs | No Nintendo BIOS or commercial ROM is tracked |
| BLD-004 | Generated HDL repeatability | Run the GHDL conversion twice | Generated Verilog hashes match |

Gate 1 passes when all four tests pass from a clean checkout.

## Gate 2: clocks, reset, and CDC

### Clock generation

- Assert that the system and panel PLL outputs are 16 MHz and 64 MHz for a
  16 MHz input.
- Count Game Boy clock enables over at least one second of simulated 16 MHz
  time. The accumulated normal-speed and double-speed pulse counts must match
  4,194,304 and 8,388,608 exactly.
- Assert that each enable is a single system-clock pulse and that no illegal
  adjacent normal-speed enables occur.

### Reset

- Exercise power-on reset, launcher reset, reset during boot, reset during a
  cache miss, and reset during save writeback.
- All requests, cache-valid bits, dirty bits, FIFOs, mapper registers, and sticky
  faults must enter their specified reset state.
- Releasing reset must not produce an SPI request until configuration is valid.

### Clock-domain crossing

- Run asynchronous SPI and system clocks with randomized phase and small
  frequency variation.
- Send at least one million frames with randomized gaps and backpressure.
- Scoreboard every byte and sequence number; no byte may be duplicated, lost,
  or reordered.
- Lint or formal CDC checks must find no unsynchronized multi-bit bus crossing.

## Gate 3: core memory and boot

| ID | Test | Pass condition |
| --- | --- | --- |
| MEM-001 | DMG WRAM/VRAM/HRAM decode | Reads return the last written value with correct mirroring and byte behavior |
| MEM-002 | CGB WRAM and VRAM banks | Every bank is independently writable and bank zero/special selector behavior matches the core specification |
| MEM-003 | OAM and palette access | Addressing, reset state, and access restrictions match the portable core reference simulation |
| MEM-004 | Open DMG boot ROM | Control transfers to cartridge entry and the boot overlay disables correctly |
| MEM-005 | Open CGB boot ROM | CGB mode, registers, palette state, and cartridge transfer match the reference simulation |
| MEM-006 | Optional BIOS validation | Only exact 256-byte DMG and 2304-byte CGB images are accepted |

Use generated 32 KiB ROMs that print a pass signature into a test register and
display a unique checksum pattern. Run each ROM in both direct BRAM mode and,
later, cached-cartridge mode.

## Gate 4: SPI protocol and cartridge cache

### Protocol tests

Cover every opcode and status bit. For each valid request, test minimum,
ordinary, and maximum permitted lengths. Inject:

- Bad magic or version.
- Unsupported opcode.
- Zero or oversized length.
- CRC corruption in every header byte and representative payload positions.
- Duplicate, skipped, old, and wrapped sequence numbers.
- Chip-select deassertion in the middle of a frame.
- Host timeout and retry.

Each fault must produce the specified sticky fault, must not commit a partial
payload, and must recover only through the defined acknowledgement/reset path.

### ROM-cache tests

Use a deterministic patterned backing image and a reference cache model.
Randomize addresses, sequential runs, bank boundaries, cache-index collisions,
and host response latency.

Verify:

- Hit data and miss-filled data match the backing image byte-for-byte.
- Least-recently-used replacement is deterministic.
- A miss cannot expose stale data.
- Only the guest cartridge access stalls; unrelated display/transport state
  continues advancing.
- Prefetch never replaces the currently demanded line and is discarded safely
  after reset or mapper change.
- Addresses at `0`, every 256-byte boundary, every mapper-bank boundary, and the
  final byte of a 4 MiB image work correctly.

Performance acceptance on hardware:

- Sustained cache-fill payload throughput is at least 1.5 MiB/s.
- 99th-percentile 256-byte fill latency is at most 400 microseconds.
- One million cache-line transactions complete with zero CRC, sequence, or
  data errors.
- A sequential execution fixture runs within 1% of the expected emulated cycle
  count after prefetch warm-up.

If either throughput or latency fails, switch to the raw contiguous flash slot
defined in `docs/plan.md` and repeat this gate.

## Gate 5: cartridge mapper matrix

Generate mapper-specific ROMs whose banks contain bank number, address, and a
checksum. Each fixture reports results through both a display signature and a
simulation-only status port.

| Mapper | Required cases |
| --- | --- |
| ROM-only | Fixed bank reads, 32 KiB boundary, writes ignored |
| MBC1 | ROM banking, RAM enable, RAM banking, mode 0/1, forbidden bank remapping, bank-boundary execution |
| MBC2 | ROM banking, address-bit-qualified commands, 512x4-bit internal RAM, high-nibble read behavior |
| MBC3 | ROM banking, RAM enable/banking, RTC register selection with static RTC behavior |
| MBC5 | Full 9-bit ROM bank, RAM bank, bank zero in switchable window, highest supported 4 MiB address |

For every mapper, test reset defaults, disabled-RAM reads/writes, rapid bank
changes, execution across a bank change, and reset while a banked cache request
is outstanding.

## Gate 6: save cache and persistence

### RTL save-cache tests

- Randomized reads and writes against a byte-accurate reference model.
- Dirty and clean eviction from both ways of every set.
- Byte writes at the beginning/end of a line and save region.
- Mapper RAM enable/disable and bank changes.
- Reset with clean data, dirty data, and an outstanding writeback.
- Host retry must be idempotent and must not acknowledge data that was not
  durably accepted into the RP2350 SRAM buffer.

### Host persistence tests

- Create missing saves at exactly the header-declared size.
- Reject or explicitly migrate an incorrectly sized existing save.
- Checkpoint an all-address pattern and compare after reload.
- Interrupt before temporary-file sync, after sync, and before/after rename.
  The next launch must see either the previous or complete new save, never a
  mixed file.
- Run 100 checkpoint cycles and verify identical final hashes.
- Confirm no flash operation occurs for individual guest save writes.

Hardware acceptance requires changing save data in a mapper fixture, performing
a clean launcher exit, power-cycling the badge, and recovering the exact data.

## Gate 7: video

### Simulation

- Feed known color bars and coordinate patterns into the RGB555 input.
- Verify RGB555-to-RGB565 conversion at black, white, primary colors, and all
  channel extrema.
- Verify exactly 160 pixels are captured per line and exactly 144 lines per
  frame.
- Randomize producer/consumer phase to force both ping-pong buffers to alternate.
- Assert that a buffer cannot be overwritten before the panel consumes it.
- Verify the panel command stream clears the display, selects window
  `(40,48)` through `(199,191)`, and transmits pixels in the correct order.

### Hardware

- Photograph or capture the coordinate pattern and verify all four corners,
  orientation, color order, and centered black borders.
- Run alternating single-pixel and checkerboard patterns to expose dropped,
  repeated, or shifted pixels.
- Count produced and consumed frames for ten minutes; the difference must remain
  bounded to the designed buffering and no underrun counter may increment.

## Gate 8: controls and audio

### Controls

- Test every physical input alone and opposing D-pad directions.
- Verify Start on `btn[2]` and launcher reset separately.
- Press A then B, B then A, and both together. Select must assert only for the
  defined chord and A/B must be suppressed while it is active.
- Hold every input for at least ten seconds and verify no repeat or release
  glitch not generated by the guest software.

### Audio

- Feed silence, DC extrema, impulses, square waves, and simultaneous channel
  output into the mixer.
- Verify saturation without wraparound and the expected mono mix.
- Measure sigma-delta average duty cycle for representative sample values.
- Run a diagnostic melody on hardware and record audio; confirm channel order,
  pitch, absence of persistent underruns, and silence after reset.

## Gate 9: launcher and validation

Test the launcher with:

- Valid `.gb` and `.gbc` files from 32 KiB through 4 MiB.
- Empty, truncated, oversized, and non-power-of-two files.
- Valid and invalid Nintendo-logo/header checksum fields.
- Every supported mapper and representative unsupported mapper values.
- `auto`, `dmg`, and `cgb` mode selection.
- Missing, read-only, incorrectly sized, and corrupt save files.
- Long filenames, duplicate stems, and characters requiring path sanitization.
- FPGA-not-ready, protocol-version mismatch, and sticky-fault states.

The launcher must keep the FPGA in reset until ROM, save, mode, protocol, panel,
and boot configuration are valid. Every rejection must show a specific reason
instead of a generic launch failure.

## Gate 10: synthesis and timing

Run synthesis for both direct-BRAM-ROM and flash-cache configurations.

Pass conditions:

- Target device and package exactly match the GreyMecha ECP5-25K.
- DP16KD utilization is no greater than 56.
- No unintended large memory is implemented in flip-flops or LUTs.
- No inferred latch, combinational loop, unconstrained clock, or unconstrained
  cross-domain path remains unexplained.
- The 16 MHz and 64 MHz domains meet timing with non-negative slack.
- The SPI input/output constraints cover the 20 MHz target and board-level
  timing assumptions are documented.
- LUT utilization above 85% is a release warning requiring a successful
  high-effort route and repeated-seed timing check.

Record utilization by subsystem where synthesis hierarchy permits: portable
core, RAM/cache, host bridge, display, and audio.

## Gate 11: end-to-end hardware bring-up

Execute in order; do not advance past a failing stage.

1. **Static board check:** correct bitstream identity, safe pin states, 16 MHz
   clock present, PLL locks, reset works.
2. **Panel/input/audio check:** test pattern, every control, and diagnostic tone.
3. **SPI stress:** status loopback followed by one million verified cache-line
   transfers.
4. **BRAM DMG boot:** generated ROM reaches pass signature with video/audio.
5. **BRAM CGB boot:** generated CGB ROM reaches pass signature in CGB mode.
6. **Cached boot:** repeat both ROMs through RP2350 flash and compare signatures.
7. **Mapper matrix:** run every generated mapper fixture.
8. **Persistence:** modify, checkpoint, power-cycle, and reload every supported
   save type/size class.
9. **Optional legal-ROM smoke:** use locally supplied ROMs to exercise menus,
   gameplay, audio, and saves; record hashes but never copy ROMs into results.
10. **Soak:** run for 30 minutes while periodically exercising inputs and save
    writes. Require zero protocol faults, cache deadlocks, video corruption,
    persistent audio underruns, or save mismatch.

## Release exit criteria

A release candidate is accepted only when:

- Gates 1 through 10 pass automatically or have captured hardware evidence.
- Gate 11 passes on the actual GreyMecha/Army revision being shipped.
- All failures have a reproducible test or an explicitly documented waiver.
- The README states the 4 MiB ROM limit, supported mappers, static MBC3 RTC,
  Select chord limitation, flash-backed storage behavior, and BIOS policy.
- The packaged hashes match the artifacts used for the final hardware soak.
